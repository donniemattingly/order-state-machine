# Order State Machine

## Run

Install [Bun](https://bun.sh/docs/installation), then:

```sh
bun install
bun start          # Run the demo and print order state + history
bun test           # Run the happy-path and failure-scenario tests
bun run typecheck  # Check TypeScript
```

Payment and fulfillment are stubbed; no external services or credentials are required.

## What I built and why

With TypeScript, I always try to make the types good enough that the implementation is almost trivial. A state machine is an obvious fit for this model. This is spiritually similar to something like Redux/useReducer in React.

This exercise is quite interesting in September of 2026. It's trivially one-shot by most any recent model, and most would produce code that's more or less fine. I haven't written actual source code in months, and I have had crises of consciousness about whether code quality even really matters.

I wanted to engage with it honestly and earnestly, which means heavy use of agentic coding tools (Astra in Codex). I uploaded the PDF and described the problem and what I saw as the salient points. I knew I was going to go with TypeScript and the shape of the solution I have here, but I wanted to see what other approaches would look like: purely imperative, heavily OO, using a library like Effect, 'best of what a few agents come up with on their own', etc. Coding is more or less solved, and any of those approaches would honestly be fine. That said, I wanted to submit the approach I was leaning towards myself.

All the lines of source code were generated by the agent, but all comments are pure corn-fed human tokens. I went back and forth with the agent until what it produced matched my expectations. Once I was satisfied, I went through and added comments.

I challenged the initial Effect-based approach because its runtime ceremony didn't feel justified for this problem. We moved to plain TypeScript, retained tagged states and explicit results, and refactored toward small named functions. Validation covered all four required outcomes, invalid transitions, overlapping operations, history integrity, and preservation of both errors when recovery fails.

## Tradeoffs

The big issue I see with what I have here is that it provides structure without guarantees. Something like the Effect library or a more robust set of type definitions might actually be able to let the compiler act almost as a static verifier, but that did not seem like an appropriate amount of ceremony here.

Honestly, what I have may not be worth the cognitive overhead compared to a few simple functions that do the naive implementation. This is more extensible in a probably not-super-meaningful way at the cost of some misdirection.

## With more time

More tests. This kind of stuff begs for mutation testing or other more black-box approaches. Ultimately, the state machine is accurate only if cast in relief of a well-specified test suite. This is also a toy version of the problem. The complexity of this problem is mostly how it scales to a full system. The real version of this problem involves queues and step functions and many other distributed systems primitives. If this is truly just something that can be handled in a single JavaScript file, then basically any approach is defensible.
